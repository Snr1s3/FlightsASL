# FlightsASL

FlightsASL is a FastAPI application that stores airport and flight schedule data in PostgreSQL.
It integrates with FlightRadar24 data, persists airports and flights, and serves both API and HTML pages.

## Features

- FastAPI backend with autogenerated OpenAPI docs
- PostgreSQL persistence for airports and flights
- Airport search and save flows
- Flight schedule fetch, filter, and store flows
- Trigger-based purge of old arrivals with purge logs
- Basic HTML pages rendered via Jinja templates

## Tech Stack

- Python 3.11+
- FastAPI
- Uvicorn
- PostgreSQL 16
- Poetry
- psycopg2
- FlightRadar24 API client

## Project Structure

- src/main.py: FastAPI app setup, middleware, static and template mounting
- src/Routes/airports.py: airport search and airport persistence endpoints
- src/Routes/flights.py: flight fetch and flight storage endpoints
- src/Routes/web.py: utility web endpoints and truncate endpoint
- src/db/db.sql: schema and indexes
- src/db/db_functions.sql: trigger function and trigger definitions
- src/docker/docker-compose.yml: app and postgres services

## Local Development

### 1. Install dependencies

poetry install

### 2. Configure database environment variables

The application reads these variables from the environment:

- POSTGRES_HOST (default: localhost)
- POSTGRES_PORT (default: 5432)
- POSTGRES_DB (default: FLIGHTSASL)
- POSTGRES_USER (default: admin)
- POSTGRES_PASSWORD (default: admin)

Note:

- The source code in src/db/db_connection.py reads POSTGRES_* variables.
- The provided Docker app image in src/docker/docker-compose.yml currently uses DB_* variables in its environment block.
- If you run the source code directly, set POSTGRES_*.

Example:

export POSTGRES_HOST=localhost
export POSTGRES_PORT=5432
export POSTGRES_DB=FLIGHTSASL
export POSTGRES_USER=admin
export POSTGRES_PASSWORD=admin

### 3. Apply schema and functions

Run the SQL files against your local database:

psql -h "$POSTGRES_HOST" -p "$POSTGRES_PORT" -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f src/db/db.sql
psql -h "$POSTGRES_HOST" -p "$POSTGRES_PORT" -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f src/db/db_functions.sql

### 4. Start the API

poetry run poe dev

The dev task runs:

cd src && uvicorn main:app --reload --port 8000

## Docker Run

From the repository root:

sudo docker compose -f ./src/docker/docker-compose.yml up -d

Stop services:

sudo docker compose -f ./src/docker/docker-compose.yml down

Important note about init scripts:

- src/db/db.sql and src/db/db_functions.sql are mounted into docker-entrypoint-initdb.d
- PostgreSQL only executes those init scripts on first initialization of a new data directory
- If you change SQL files later, re-apply them manually or recreate the volume

Recreate database volume (destructive):

sudo docker compose -f ./src/docker/docker-compose.yml down -v
sudo docker compose -f ./src/docker/docker-compose.yml up -d

## API Overview

### Airports

- GET /api/airport/search?name=BCN
	Search airports via FlightRadar24-backed lookup.

- POST /api/airport/save
	Save an airport to PostgreSQL.

- GET /api/airport/all
	Return airports marked as search=true.

### Flights

- POST /api/flights/storeFlights?iata=BCN&type=1&limit=100&page=1
	Fetch flights from provider, filter by time window, and store in DB.
	type=1 means arrivals, other values mean departures.

- GET /api/flights/getFlights?iata=BCN&type=1&limit=100&asc=1
	Query stored flights for an airport from PostgreSQL.

### Utility Web Endpoints

- GET /web/welcome
	Returns a welcome JSON response.

- DELETE /web/dropAll
	Truncates flights and airports tables and resets identity counters.

## Database Notes

- airports and flights use SERIAL primary keys (backed by PostgreSQL sequences)
- flights.id_flight has uniqueness and length checks
- purge_old_flights_by_arrival trigger function removes old arrivals
- PURGE_INFO logs purge runs with created_at and removed_count

## Troubleshooting

- Docker compose file not found:
	Use the file flag, for example:
	sudo docker compose -f ./src/docker/docker-compose.yml up -d

- SQL changes not applied in Docker:
	Init scripts run once for a fresh postgres data volume only.

- Database connection in local run:
	Ensure POSTGRES_HOST, POSTGRES_PORT, POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD are set correctly.

- Running app from source in Docker and getting DB errors:
	Use POSTGRES_* variables for the source app, or adapt compose environment names to match the app you are running.
